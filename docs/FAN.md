# 风扇控制

让机器在发烫时真正凉下来。**只提速，不降速。**

---

## 一、Apple Silicon 上到底怎么控制风扇（实测）

三次实测才走通，过程记录在这里，省得别人重踩。

### 第一次：只写 `F0Tg` —— 静默失败

```
【基线】不干预        F0Tg 2559 → 2557 → 2555 → 2553   ← 固件自己在持续微调
【写入】F0Tg = 3000   SMC 返回 ✅ 成功
【4 秒后】            F0Tg = 2554   转速 2557          ← 被固件覆盖回去了
【16 秒后】           F0Tg = 2551   转速纹丝不动
```

**SMC 接受写入并返回成功，但固件几秒内就把目标改回自己的判断。**
如果不做这个实测就交付，用户会得到一个"看起来能用、实际什么都没发生"的功能。

### 第二次：先写模式键 `F0md` —— 成功

枚举全部 `F*` 键时发现了 **`F0md`（小写 md）**。
Intel 时代的 `FS! ` 和 `F0Md`（大写 M）在 Apple Silicon 上**都不存在**，这是第一次误判的原因。

```
【写 md=1】     回读确认 F0md=1 F1md=1                    ✅
【写 Tg=3400】  实际转速 3397 → 3404 → 3401 → 3409        ✅ 稳定保持 20 秒
【写回 md=0】   F0Tg 立刻回到 2325 → 2315（重新自己飘）    ✅ 固件完整收回控制权
```

**结论：必须先 `F0md = 1` 取得手动控制，再写 `F0Tg`。顺序反了就静默失效。**

### 第三次：温度传感器选错了 —— 曲线永远全速

最初按"读数最高"挑温度传感器，结果选中的全是**限值寄存器**：

```
候选 322 个 → 3 秒内会变的 294 个，纹丝不动的 28 个

真实传感器（有变化）              恒定不变（限值寄存器）
TVDc  79.4 → 80.1 °C             Tf06 : 97.3 °C  ← 一直不动
TCMb  80.2 → 78.7 °C             Tf16 : 95.1 °C  ← 一直不动
Tp00  73.2 → 73.9 °C (P核)       Tp0u : 63.4 °C  ← 一直不动
```

`Tf06` 永远是 97.3°C。用它驱动曲线，风扇会永远全速 —— 又是一个"看起来在工作、逻辑其实是错的"。

**正确做法：按变化量识别。** 隔 2 秒采样两次，只保留读数发生变化的键；
若变化的太少（机器完全空闲）则退回 `Tp*` / `Te*` / `Tg*` 前缀白名单。

## 二、本机硬件参数

```
FNum : 2 个风扇
F0   : 1350 – 5349 RPM
F1   : 1350 – 5777 RPM
SMC 键总数 3668，可读温度传感器 322 个（其中 28 个是限值寄存器）
```

`AppleSMC` **非 root 就能打开并读取**；**写入需要 root** → 走已有的 `lidawaked` 守护进程。

## 三、四种模式

| 模式 | 行为 |
|---|---|
| **自动** | 交还固件（默认） |
| **百分比** | `目标 = Mn + pct×(Mx−Mn)`，作为**下限**施加 |
| **全速** | 直接 `Mx` |
| **按温度自动** | 低于起点不干预；起点→终点之间线性爬升；终点以上全速 |

```bash
lidawake fan              # 看当前状态
lidawake fan curve        # 按温度自动
lidawake fan 70           # 固定 70%
lidawake fan full         # 全速
lidawake fan auto         # 交还系统
lidawake fan curve --start 75 --full-at 92 --critical 98
```

## 四、为什么是「只提速不降速」

用户要的是更凉快。**"把风扇压到比固件认为需要的还低"才是能把机器捂坏的方向**，
所以本实现从构造上就不提供 —— 这是与 ChillMac / Macs Fan Control 这类"手动滑块"最大的区别，
它们的滑块是可以往下拉的。

实现方式是一条**随温度上升的安全下限**：

| 最高温 | 允许的最低转速 |
|---|---|
| < 75°C | 不限制 |
| 75–85°C | ≥ 35% |
| 85–90°C | ≥ 60% |
| 90–95°C | ≥ 80% |
| ≥ 95°C | **100%** |
| ≥ `criticalC`（默认 100°C） | **无条件全速，覆盖任何用户设置** |

实测例证：设 `fan 70` 时机器 97°C，实际跑到了 **5347 RPM（100%）** —— 下限把它顶上去了。

## 五、失效安全

和 `SleepDisabled` 同一套纪律：

| 事件 | 行为 |
|---|---|
| SIGTERM（关机 / 卸载 / `bootout`） | 写回原目标 + `md=0`，交还固件 |
| 守护进程崩溃 | launchd 拉起 → 启动时无条件 `release()` |
| **重启** | 风扇模式**永不跨重启保留**，一律复位为自动 |
| 空闲自退 | 先交还固件再退出 |
| 手动模式期间 | 守护进程**绝不空闲自退**（否则没人在温度变化时重新评估，更没人交还控制权） |

最后一条由 `Engine.shouldIdleExit(mode:connectedClients:fanMode:)` 保证，有单测锁定。

## 六、对 XPC 协议的影响

协议从"只能表达 `off` / `indefinite` / `until(秒数)`"扩展为**再加上风扇模式**。

要点：**新增字段仍然只有枚举与数字，没有任何路径、命令或 shell 参数。**
服务端 `FanRequest.validated()` 会把百分比夹到 0–100、曲线阈值夹到合法区间。
所以"即使鉴权被绕过，攻击面上限也只是让机器不睡觉/让风扇转快"这个性质保持不变。

## 七、测试

单元测试 34 项覆盖纯函数决策引擎（`FanEngine.decide`）：
优先级、安全下限各温度档、量程非法/颠倒、曲线边界、策略 clamp、编解码、自退判定。

真机验证（需 root）：

```
初始      自动    2216/2383 RPM   固件控制中
fan 70    →       5347/5345 RPM   ← 97°C 时被安全下限顶到 100%
fan full  →       5345/5349 RPM
fan auto  →       1347/1461 RPM   固件控制中  ← 交还成功
fan curve →       4848/4866 RPM   目标 4818   ← 中间值，非全速
```
